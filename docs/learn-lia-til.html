Orient

00 · How to read a codebase

Nobody reads code top-to-bottom like a book. You follow one thing through the system. The most useful thread here is a single piece of data — say, "the number 129 on the Applications page" — and you trace it from where it's stored to where it's shown.

The repo is two apps plus docs:

lia-til/
├─ web/            # the FRONTEND — Next.js, deploys to Vercel
│  ├─ app/         # every folder = a URL (App Router)
│  ├─ lib/         # server-only helpers (auth, data fetch)
│  └─ content/     # committed JSON snapshots (the fallback)
├─ backend/        # the BACKEND — FastAPI, deploys to Render
│  ├─ main.py      # the API endpoints
│  ├─ models.py    # the database tables (as Python classes)
│  ├─ db.py        # the Postgres connection
│  └─ import_*.py  # scripts that load data into the DB
└─ docs/           # the walkthrough + this guide

Two mental hooks to hold the whole time:

1. Frontend vs backend = two separate deployments. web/ lives on Vercel (URL ends .vercel.app); backend/ lives on Render (URL ends .onrender.com). They talk over HTTP. This is why the same secret has to be set in two places — you hit exactly this when the login broke.

2. Follow the data. Every feature is the same journey: something is stored, an endpoint serves it, a page fetches and renders it. Learn that spine once (Part 2) and every page is the same shape.

Part 1 · The stack, as choices

01 · Why Next.js + Vercel

Pain

You wanted a public site that you could keep changing without emailing files to a server every time — and it had to be free and look decent.

A plain HTML file would work, but the moment you want many pages, shared layout, and "push to update," you're hand-rolling a framework. Next.js gives you file-based routing (a folder = a URL), server rendering, and a first-class host (Vercel) that redeploys on every git push. That auto-deploy pipeline is the reason the very first stage existed: prove "edit → push → live" before building anything real.

Next.js + Vercel frontend
Why it won

Folder-based routing, SSR + static, and git push → live in ~30s. React means components you already half-know.

What it traded away

A build step and framework weight vs a raw HTML file. You now must know its rules (Server vs Client components, dynamic rendering).

Named rival

Plain HTML/CSS (too manual past a few pages) · Create-React-App / Vite SPA (no server rendering, no built-in routing/host).

When you'd switch

A truly static one-pager with no shared layout → plain HTML. A heavy client app with no SEO need → a Vite SPA.

"Why did you use Next.js?" — which answer scores a 5 in an interview?

1–2/5. That's a definition ("X is a…"). Definitions are free to look up, so they score near zero. The interviewer wants the choice.
5/5. Names the constraint (shared layout + deploy), the rival (HTML / Vite SPA), the cost, and the switch condition. That last clause is what turns a 4 into a 5.

02 · Why a backend at all — FastAPI + Neon + Render

Pain

With everything baked into the site, every content change meant a code change + a rebuild. You wanted one place that holds the truth, and updates that show up instantly. You also wanted the résumé to say "I built a backend."

So Phase 2 added a real backend: a database as the single source of truth, and an API in front of it. Three picks, each with a reason:

FastAPI the API
Why it won

Python (you're learning backend in Python), tiny to stand up, auto-generates API docs, typed request/response.

Traded away

You run a server process (vs "just functions"). More to host and keep awake.

Named rival

Express/Node (would've meant JS on both sides, but you want Python on the résumé) · Django (heavier, batteries you don't need).

Switch when

You need Django's admin/ORM ecosystem, or a Node-only shop.

Neon Postgres the database
Why it won

Real SQL Postgres, serverless + free, scales to zero when idle. "Postgres" is the résumé-legible skill.

Traded away

Cold start after idle (first query wakes it). A pooled vs direct connection gotcha to remember.

Named rival

SQLite (a file — dies on a serverless host) · MongoDB (your data is tabular + relational; SQL fits) · Firebase (locks you into its SDK).

Switch when

Document-shaped data with no joins → a document DB.

Render the host
Why it won

Free web-service tier, auto-deploys from GitHub like Vercel does. Simple.

Traded away

Free tier sleeps after 15 min idle → ~30–60s cold start on the first hit.

Named rival

Railway (free tier gone) · a Vercel serverless function (would fold API into the frontend — but "I ran a separate FastAPI service" is the better story, and Python functions on Vercel are fiddlier).

Switch when

You need no-cold-start / real traffic → a paid tier or a container on a cloud VM (that's Phase 3).

Part 1 · The stack, as choices

03 · The instant-sync trick

Pain

Even with a backend, if pages were pre-built, a data change still wouldn't show until a rebuild. You wanted: change the data → refresh → it's there.

Next.js normally pre-renders pages at build time (fast, but frozen). The fix is one line per page: export const dynamic = "force-dynamic". That tells Next "render this on every request," so the page re-fetches the API each time you open it. No rebuild, no git push — the DB is the source, the page just reads it live.

// web/app/applications/page.tsx
export const dynamic = "force-dynamic";   // render per request, not at build

async function getSummary() {
  const base = process.env.API_URL;
  try {
    const res = await fetch(`${base}/api/applications/summary`, { cache: "no-store" });
    if (res.ok) return res.json();     // live from the backend
  } catch {}
  return committedSnapshot;             // fallback if the API is down/asleep
}
🔁

The content/*.json files in the repo are the fallback, not the source. If Render is asleep or unset, the page still renders yesterday's committed snapshot instead of breaking. Live data preferred, static safety net underneath.

Check 03selection · /5

What did force-dynamic buy, and what did it cost?

5/5. Every technique buys something by selling something. Here: freshness bought at the price of a per-request fetch + a dependency on the backend — which is exactly why the fallback exists.
Wrong model. force-dynamic is the opposite of caching — it re-renders every request. And it's about server rendering timing, not Client Components. Reset the model: dynamic = fresh-but-slower; static = fast-but-frozen.

Part 1 · The stack, as choices

04 · Why custom OAuth, not a library

Pain

You needed a login so only you can see the private ledger. The obvious move is a library (Auth.js/NextAuth). But this Next.js is version 16 — brand new — and it renamed middleware to Proxy, which Auth.js v5 leans on. Risky.

So instead of a library we hand-wrote the standard OAuth2 authorization-code flow + a signed session cookie — which is exactly the pattern Next's own docs endorse. For a single user, it's ~120 lines you fully control, and "I implemented OAuth" is a far better interview story than "I installed a library."

Custom OAuth + jose session auth
Why it won

No dependency fighting a v16 breaking change; total control; you understand every line; great résumé/interview material.

Traded away

You own the security details (CSRF state, cookie flags) yourself — a library would handle those. Fine for one user; not for many with password reset, roles, etc.

Named rival

Auth.js / NextAuth (leans on the renamed middleware) · Clerk/Auth0 (hosted, but overkill + another vendor for a one-person gate).

Switch when

Multiple users, social + email logins, roles, or you don't want to own security → a library or hosted provider.

Check 04selection · /5

"Why not just use NextAuth?" Which is the interview-grade answer?

≤2/5. "More secure by hand" is a wrong model — rolling your own auth is usually less safe; the honest reason is version compatibility + scope, not superiority. "I don't like dependencies" is taste, not selection.
5/5. Concrete constraint (the v16 rename), honest scope (one user), and a clean switch condition (more users → library). Note it does not claim hand-rolled is safer.

Part 2 · API design — the layers

05 · The six-layer pipeline

This is the part you said felt tangled. It's actually one shape, reused for every feature. Data flows down through six layers, each doing exactly one job. Here it is, with the file that owns each layer:

1Source · the raw truth you editledger.md · content/*.json
2Importer · reads source → writes DBbackend/import_*.py
3Database · stores it (tables = classes)models.py · Neon
4API endpoint · returns JSON over HTTPbackend/main.py
5Frontend fetch · page asks the API (or falls back)app/**/page.tsx
6Render · turns JSON into HTML you seethe same page.tsx

Why so many layers? Each boundary buys a freedom:

• Source ≠ DB lets the source be a private file on your laptop (the applications ledger never enters the public repo) while the DB holds it privately in the cloud.
• Importer is the one-way bridge — you run it, it's where "curate the public subset" happens.
• DB ≠ API means the API decides what leaves the building (aggregates only, unless you're authed).
• API ≠ page means the frontend and backend deploy and scale independently.

One concrete trace: the "129 applications"

Your private ledger (source) → import_ledger.py reads it and writes rows into the applications table (DB) → /api/applications/summary counts them and returns {totalSubmitted: 129, ...} (endpoint) → the Applications page fetches that (frontend) → renders "129" (render). Change the ledger, re-run the importer, refresh — 129 becomes 130. No push.

Check 05trace

You add a job to your ledger but the site still says 129 after refresh. Which layer is the culprit?

Right. The source and the DB are deliberately separated by the importer bridge. "I changed the source" ≠ "the DB changed." This is the whole reason the pipeline has that seam — and knowing which layer to suspect is what "understanding the design" means.
Re-trace it. The page + endpoint faithfully report whatever the DB holds — and the DB is still 129 because nothing wrote to it. The break is upstream: the importer hasn't run.

Part 2 · API design — the layers

06 · Public vs private endpoints

Pain

The DB holds everything — every company you applied to, salaries, notes. But the public site must show only counts. Same data, two very different audiences.

The design answer: the endpoint layer is the gatekeeper. The same applications table is exposed through two endpoints with different rules:

DBapplications table · full private rowsmodels.py
A/api/applications/summary · counts only — anyonepublic
B/api/applications/full · every field — needs the secretX-Admin-Secret

Endpoint A runs a COUNT(*) and returns aggregates — no company name ever leaves. Endpoint B returns full rows but is fail-closed: without the right secret header it returns 401, and if the secret isn't even configured, it still returns 401. Deny by default.

# backend/main.py
def require_admin(x_admin_secret = Header(default=None)):
    if not ADMIN_SECRET or x_admin_secret != ADMIN_SECRET:
        raise HTTPException(status_code=401)   # fail-closed

# public: aggregates only
@app.get("/api/applications/summary")
def summary(): ...          # returns {totalSubmitted, byStatus, byDate}

# private: gated by the secret
@app.get("/api/applications/full", dependencies=[Depends(require_admin)])
def full(): ...             # returns every company + note
🔑

The browser never holds that secret. It lives on the servers only. The private page checks your login, then the Next.js server calls endpoint B with the secret — server-to-server. A logged-out visitor never gets near it.

Check 06selection · /5

Why two endpoints instead of one endpoint that returns full data "only if logged in"?

5/5. This is the same reasoning as choosing a separate /private route: put the privacy boundary in the structure, not in a runtime if. Structure can't be forgotten in a refactor. (Rival: one gated endpoint — simpler, but one mistake from exposure.)
No. It's not about speed or a framework rule — it's a privacy-by-structure decision. The public code never importing the private fields is the safety property.

Part 3 · Authentication — the wiring

07 · Why a third party (yes — that SMS)

Pain

You need to prove you are you before showing the private ledger. But you do not want to build passwords, store them, handle "forgot password," get hacked. Identity is a whole industry.

So you borrow it. GitHub already knows who you are — it has your password, your 2FA, your phone. Instead of building your own login, you ask GitHub: "is this person really patelinadev? If yes, tell me." That's third-party auth.

📱

That surprising SMS was GitHub, not your code. When you clicked "Authorize," GitHub ran its own verification of you — including texting your phone. Your code never saw your password and never saw that SMS code. That's the entire point: you outsourced "prove it's really Lia" to the company that's good at it. Your code only ever receives GitHub's verdict afterward.

The valet-key analogy

OAuth is a valet key. You don't hand the valet your house keys and wallet (your password). You hand a limited key that only starts the car (a token that can only read:user — your public profile). Your app gets the valet key, uses it once to ask "who is this?", and throws it away. It never learns your password.

Check 07mental model

Where did your GitHub password go in this whole flow?

Exactly. This is why OAuth exists — the password only ever meets the party that issued it. Your app trusts GitHub's answer instead of handling credentials itself. That's the "magic" demystified.
Wrong model — important to fix. If your app ever touched the password, you'd have inherited all the risk you were trying to avoid. It doesn't. You typed it on github.com; your app only gets a token back.

08 · The OAuth dance, step by step

Now the wiring — every step mapped to a file. Orange steps happen on GitHub; teal steps are your code. Read it twice: this is diagram #2 you need to draw from memory.

1

Click the corner 🔒 → go to /private.
2
code · app/private/page.tsx
requireAdmin() finds no session → redirect("/api/auth/login").
3
code · api/auth/login
Set a random CSRF state cookie, then redirect to GitHub's authorize URL with client_id + state + scope=read:user.
4
github.com
GitHub verifies you (password, the SMS) and shows "Authorize lia-til?". You click yes.
5
github.com
GitHub redirects back to /api/auth/callback?code=…&state=…. The code is a one-time voucher.
6

Check state matches the cookie (anti-CSRF). Then POST the code + client_secret to GitHub → get an access token.
7
code → github api
Use the token: GET api.github.com/user → { login: "patelinadev", … }.
8
code · the allowlist
Is login === ALLOWED_GITHUB_LOGIN? If no → /private/denied. If yes → continue.
9

createSession() signs a JWT with your login and drops it in an HttpOnly cookie. Redirect to /private.
10
code · app/private/page.tsx
This time requireAdmin() finds a valid session → renders the page. Done.
🧭

Why the state cookie (step 3 & 6)? Without it, an attacker could trick your browser into completing a login they started. The random value you set in step 3 must come back in step 5, or step 6 rejects it. That's CSRF protection — a detail a library would hide, and one you now own.

Check 08the wiring

GitHub sends back a code (step 5), not the token directly. Then step 6 swaps it for the token. Why the extra hop?

Yes. This is the heart of the authorization-code flow: the thing exposed in the browser (the code) is single-use and useless alone; the powerful token is only fetched in a back-channel call that also proves your app's identity with the secret.
Re-read step 6. The code and token are different. The two-step design exists precisely so the token never rides through the browser — only the disposable code does.

Part 3 · Authentication — the wiring

09 · Sessions & secrets: who holds what

After login you don't re-do the GitHub dance on every click. Step 9 gave your browser a session cookie — a signed note that says "this is patelinadev, verified." Three different secrets do three different jobs; mixing them up is where the confusion lives:

1AUTH_SECRET · signs the session cookie so it can't be forgedVercel · session.ts
2GITHUB_CLIENT_SECRET · proves your app to GitHub in step 6Vercel · callback
3BACKEND_SECRET · frontend→backend password for private dataVercel AND Render

The session cookie is a JWT: a small signed token holding just { login, name, avatar }. Signed with AUTH_SECRET (HMAC), so if anyone edits the cookie the signature breaks and it's rejected. It's HttpOnly (JavaScript can't read it), Secure (HTTPS only), and expires in 7 days. It holds no GitHub token and no password — the minimum to know it's you.

requireAdmin() is the guard on every private page: read the cookie → verify the signature → check the login is on the allowlist → return the session or redirect to login. And secret #3 is the one that bit you: it must be identical on Vercel and Render, because the frontend sends it and the backend checks it. Different values → the backend says 401 → the private table comes back empty.

Check 09diagnose

You log in fine, but /private/applications shows an empty table. Which secret, and why?

Nailed it. "Login worked but private data is empty" is the tell: authentication (secrets 1 & 2) succeeded; the failure is the data call (secret 3). Being able to point to the exact secret from the symptom is what "understanding the wiring" means.
Re-trace. If AUTH_SECRET or the GitHub secret were wrong, you couldn't have logged in at all. You did — so the break is downstream, at the frontend→backend data call: BACKEND_SECRET.
