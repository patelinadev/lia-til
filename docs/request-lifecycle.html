🔑 Two gates, two different secrets — and neither ever reaches your browser

1AUTH_SECRET signs & verifies your session JWT on the Vercel server — it proves “you are the admin.” Fail → 307 to login, and FastAPI is never called.
2BACKEND_SECRET is the x-admin-secret header on the server→FastAPI call — it proves “this call is from our own server.” Server-to-server only; the browser never sees it.

Why you never "see" the 307

A redirect is a normal HTTP response — the browser follows it on its own, so you only land on the final page (the GitHub login), never a "307" screen. The server says "not here, GET this other URL instead", and the browser silently sends that next request. That is exactly what you described — you reverse-engineered the 307. To actually watch it: DevTools → Network (tick "Preserve log") → you'll see /private 307 → /api/auth/login 307 → github.com.

Incognito has three states — the branch above is only the first:

① before login → no cookie → 307 to login · ② logging in → the callback sets the cookie in this incognito session · ③ after login, same window → cookie present → the page renders (no 307). A brand-new incognito window is back at ① and re-asks you to log in — that's correct, not a bug (no cookie = must authenticate).

Branch · not logged in (incognito)

Everything is the same until step 3. An incognito window sends no cookie:

// lib/session.ts const token = (await cookies()).get("lt_session")?.value; // undefined if (!token) return null; // getSession() → null // lib/auth.ts isAllowed(null) → false → currentAdmin() → null if (!session) redirect("/api/auth/login"); // requireAdmin bounces you

→ the server returns HTTP 307 → /api/auth/login. Steps 4–7 never run. FastAPI and the database are never touched.

Read it as three columns of value

  • Cookie in (step 1) → the browser's only job: send the request + the lt_session JWT.
  • Session out (step 3) → getSession() turns that cookie into { login, name, avatar } — or null. This decides everything.
  • Data out (step 5) → FastAPI returns { total, applications: [...] }, but only after the secret matches. Reached only if step 3 said "yes".

/private/daily-log · line by line

A second request — the filter lives in the URL

Now a different page: the private Daily Log. You turn on a tag filter, click a day, then page to the one before it — and the filter follows you the whole way. The trick: there is no shared client store. The filter is written into the URL, and each side reads it back. The two secret gates are exactly the same as the first trace (JWT on the Vercel server, then x-admin-secret to FastAPI) — so here we zoom in on the filter → URL → filtered pager mechanic instead.

One codec, two readers — web/lib/daily.ts

filterToQuery(f) turns the filter into a query string; parseFilter(searchParams) turns it back. The client list writes it (and appends it to every day link); the server day page reads it. Because both call the same two functions, the list and the pager can never disagree about what "filtered" means. Compact keys: q search · w/m/d week/month/day · tin tags-in · tex tags-out.

Why the URL is the state

  • No shared store → the client list and the server day page never talk directly. The URL is the handoff, so a link (or a refresh, or a shared URL) reproduces the exact filtered view.
  • One codec, both ends → filterToQuery (list writes) and parseFilter (day page reads) are inverses in lib/daily.ts; the pager reuses filterEntries, so "filtered" means the same thing everywhere.
  • The pager drops day → paging walks the filter minus the single-day pin ({ ...filter, day:"" }), so ↑/↓ move through the whole filtered range, not a set of one.
  • Tags are labels, not secrets → they're served on the public list too; only the per-day sections stay behind the two gates.

The other direction — writing the DB (CRUD)

The trace above is a read that starts in the browser and passes both gates. A write has no browser and no session — it's a direct call carrying only gate ②'s BACKEND_SECRET. This is how the daily log / tags / sections are edited now — no local files:

# a skill / script / cloud cron — never the browser source ~/.til-env # loads BACKEND_SECRET (chmod 600, git-ignored; the value is never printed) curl -sX PUT https://lia-til.onrender.com/api/daily-log/2026-08-19 \ -H "x-admin-secret: $BACKEND_SECRET" -H "content-type: application/json" \ -d '{"week":"W34","sections":{"Tech":"…"},"tags":["leetcode"]}'
→ FastAPI require_admin (gate ②) checks the secret · Pydantic validates the body (bad shape → 422) · the row is written to Neon · live instantly on /private/daily-log, no rebuild, no local step.
  • Only gate ② runs. No lt_session cookie, no AUTH_SECRET — that's a browser-session thing; a write authenticates purely with the shared BACKEND_SECRET (the shell expands $BACKEND_SECRET, so its value is never seen or logged).
  • The secret boundary is the same as the read. Private sections are stored but the public GET /api/daily-log filters them out — Success Diary / interview / company text can't leak.
