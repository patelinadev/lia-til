  2. 2
    /leetcode

    All 15 solved problems, filterable & sortable

    #ProblemTopicDifficultyStatusDate
    42Trapping Rain WaterTwo PointersHardFirst pass08/05
    713Subarray Product Less Than KSliding WindowMediumFirst pass08/10
    • Columns: Problem + Solution links · Topic (multi-select, each a distinct color via golden-angle hue) · Difficulty · Status (5 states in 3 groups) · Date (last completion). All scraped from 0x3f-study-plan.md; dates recovered from the daily-log sweep.

    • Scroll-reveal micro-animation — nodes fade + slide in on scroll, via a tiny IntersectionObserver client component (app/components/Reveal.tsx). Zero dependencies; respects prefers-reduced-motion.
    • LeetCode kept in the log — a day's LeetCode problems render as ✓ chips matching the done items. Each links only to Lia's own solution write-up (un-linked if no solution yet). Solution URLs are single-source in leetcode.json, looked up by id — so adding one there auto-fills the log.
    • 20 curated days scraped from the Obsidian daily logs, privacy-filtered.
    LanguageEnglish-only, no exceptions — every field of the daily log (to-dos, summaries, and the 📝 note) is English, same as the rest of the site.
  4. 4

Privacy (applies to every update)

Obsidian source files never enter the repo. The repo is public, and the logs contain sensitive material (PhD applications, Success Diary, contact info). We curate rather than sync: only the publishable subset ships (solution links + study-type checked items + a one-line summary you approve). Sensitive items are excluded by default, each passed through a §6 warning check for you to confirm.

Example (8/16): the original had "application material audit (SOP / CV / recommendation letters / deadline)" — revealing grad-school applications — so it was genericized to "Reviewed application materials"; the application count was kept.

Troubleshooting

Q1Render build fails / 502 Bad Gateway
Check Root Directory = backend, and that the Start Command binds $PORT (--host 0.0.0.0 --port $PORT).
Q2First load after idle is slow (~30–60s)
Normal — the free Render instance sleeps after 15 min idle and wakes on the next request. Fine for a low-traffic personal site.
Q3Database connection error
Neon needs sslmode=require (already in the string). Make sure DATABASE_URL in Render exactly matches Neon's.
Q4CORS error
We fetch the API server-side (Next.js), so the browser never calls Render directly — no CORS. (If we ever call it from the browser later, add CORS on FastAPI.)
Q5Is my full application data safe on a public URL?
Yes — Neon holds the full data privately; only /summary (counts) is public. Full detail comes behind login in S2.

LeetCode✅ live

Powers /leetcode. Same four artifacts — the only new twist is preserving the 0x3f plan order.

① Table
Added LeetcodeProblem to backend/models.py → table leetcode_problems, columns: id (PK, the LC number) · seq · slug · title · topics (JSON) · ep · difficulty · status · date · solution_url. Why seq: it stores the row's position in the 0x3f study plan so the list keeps that exact order (not sorted by id).
② Endpoint
Added GET /api/leetcode to backend/main.py. Returns {track, trackUrl, updatedAt, problems} with problems ordered by seq (the plan order). This same table is what the daily-log endpoint reads for solution links.

Wrote backend/import_leetcode.py — reads web/content/leetcode.json and writes each problem, setting seq from the array index (so file order = display order). Run:

④ Page
Set web/app/leetcode/page.tsx to force-dynamic and made it fetch ${API_URL}/api/leetcode (fallback: committed leetcode.json), then hand problems to the existing client-side table (filter/sort stay in the browser).

To update: you send a solved-problem or solution link → I edit web/content/leetcode.json (add the row / set solutionUrl) → run the importer → both /leetcode and the daily log's ✓ chip update on refresh.

P2 · S3

GitHub login + private view

✅ Done v0.5.0

Add a login so only you can see the private full view. Signed in with GitHub, you unlock /private — the full per-company ledger. Everyone else sees the same public, aggregate-only site as before. Live — the OAuth App and env vars are configured; verified end-to-end (logged-out /private redirects to login, the backend's private endpoint is 401 without the shared secret).

Design — why not a libraryThis Next version renames middleware → Proxy (proxy.ts), which Auth.js v5 leans on — risky on such a new release. So instead of a library we use the first-party pattern the Next auth docs endorse: the GitHub OAuth2 authorization-code flow + a jose-signed JWT in an HttpOnly cookie. Fewer moving parts, and a real "I implemented OAuth" interview story. A single-user allowlist (ALLOWED_GITHUB_LOGIN) means only your account passes.
Privacy (option B)The private full view lives at its own route /private. The public pages' code never touches private data — so it structurally can't leak. /private is also where the S4 admin editor will live.
Secrets ruleYou create the OAuth App and generate + paste every secret; I only tell you what each value is and write the code — I never see the values (same as DATABASE_URL).

The code (already shipped)

My half — done & pushed. Here's exactly what's in the repo, for rebuild reference.

Session
web/lib/session.ts — signs a JWT (HS256, secret AUTH_SECRET) holding just {login, name, avatar} and stores it in an HttpOnly / Secure / SameSite=lax cookie (7 days). Never stores the GitHub token.
OAuth flow
Three route handlers under web/app/api/auth/: login (sets a random CSRF state cookie → redirects to GitHub) · callback (checks state → swaps the code for a token → fetches the GitHub user → allowlist check → mints the session → /private) · logout (clears the cookie).
Gate
web/lib/auth.ts — requireAdmin() redirects non-admins to login; only ALLOWED_GITHUB_LOGIN counts as admin.
Pages
web/app/private/page.tsx — protected; fetches the full ledger and renders it. /private/denied — friendly refusal for a non-allowed login or a broken round-trip.
Backend
GET /api/applications/full in backend/main.py returns the full per-company rows, gated by an X-Admin-Secret header (fail-closed: no/wrong secret → 401). The Next server sends it only after verifying your session. Public /summary is unchanged.

Data flow: browser → /private (verify session) → server-to-server fetch with the secret → backend full rows. The secret and the full data never reach the browser of a logged-out visitor.

Troubleshooting

Q1GitHub says "redirect_uri mismatch"
The OAuth App's Authorization callback URL must be exactly https://lia-til.vercel.app/api/auth/callback — no trailing slash, https, right domain.
Q2I log in but the table is empty
BACKEND_SECRET on Vercel and Render don't match (or the backend hasn't redeployed). Make them identical and redeploy the backend.
Q3I get "denied" even though it's me
ALLOWED_GITHUB_LOGIN must equal your GitHub username exactly (case doesn't matter). Fix it on Vercel and redeploy.
Q4/api/auth/login returns a 500
GITHUB_CLIENT_ID isn't set on Vercel yet, or the deploy predates adding it — redeploy after setting the vars.
Q5I set the vars but still get {"error":"GITHUB_CLIENT_ID not set"}
The #1 gotcha. Vercel bakes env vars into a deployment at deploy time — a deployment that was already running when you added the var does NOT see it. Fix: after adding/changing any var, Redeploy (Deployments → latest → ⋯ → Redeploy), then retry. Also make sure the var is on Vercel (the frontend), not Render — the "not set" error comes from the Next app, so Render env vars don't help it. Frontend vars → Vercel; backend's BACKEND_SECRET → Render.

Extended — backend cold-start resilience + keep-warm (v0.5.3)

A bug surfaced right after the v0.5.2 deploy: the public /applications total was stuck at 114 and the private pages were empty, even though the DB already had 129 (8/19). Status: 🚧 code live · the keep-warm ping is your step (below).

Root cause — Render cold startThe backend runs on Render's free tier, which spins the instance down after ~15 min of no traffic; waking it takes ~40s (proven: a /health curl took 42s, then returned fresh data). A cold instance fails the first requests fast, so each page fell back to what it had — the public pages to their committed snapshot (applications.json = the "stuck at 114" number) and the private pages to empty. A browser never waits ~40s, so across devices it looked permanently stuck. Nothing was actually broken — the data + API were fine the whole time.
Design — 3 layers of defense① keep-warm ping (prevent cold): an external cron hits /health every 5 min so the idle timer never reaches 15 min. ② retry (survive a cold hit): a server-side fetch that waits the instance awake instead of falling back. ③ fresh snapshot (survive a full outage): keep the committed fallback current. Layer ① is the real fix; ② and ③ are safety nets. Note: ② and ③ can't be skipped in favour of "just hardcode the number" — a snapshot goes stale on the next application, and the private pages have no snapshot at all, so only the live fetch can fill them.
Retry helper
New web/lib/net.ts → fetchJsonWithRetry(url, init, opts): a server-side fetch that retries within a ~50s budget (per-attempt AbortController timeout + a short gap), so a request now waits a cold instance awake — like curl does — and renders live data. A 401/403 short-circuits to null (a bad secret won't fix itself by retrying).
Wired in
All four backend fetchers now use it — public getSummary() / getDailyLog() and private getFullApplications() / getFullDailyLog() — and those four pages set export const maxDuration = 60 so Vercel allows the wait.
Honest empty states
The private fetchers now return null (backend unreachable) vs [] (ledger truly empty). The pages show a calm "backend may be waking up — refresh in ~30s" notice for null, instead of the old misleading BACKEND_SECRET error.
Snapshot + cleanup
Refreshed web/content/applications.json to the current aggregate (129, 8/19) so even a full outage shows current-ish numbers. Also removed the stale "Updated <date>" line from the public /applications header (it only ever reflected the snapshot's date).

CRUD write API — cloud-only data

✅ Done v0.6.0

End goal: get rid of local files. Today the source of truth is local JSON (web/content/* + the private ledger); Claude edits them and a local import_*.py reloads the DB. This stage flips it — Neon becomes the single source of truth, edited through a secret-gated CRUD API in the cloud. After it, every create / update / delete is one HTTP call: no local files, no importer, no laptop in the loop.

Why NOT migrate the DBThe trigger was "I want to edit data via API, not from local." That does not need a different database — Neon is already cloud and already the serving source. What changes is the write path: from "local file → importer → DB" to "API → DB". Neon stays; we add the write layer on top of the 4 tables.
Decision — no fallbackThe public pages currently fall back to the committed web/content/*.json when the API is down (the "129 snapshot"). Once the DB is source of truth, that fallback goes away: on a backend error the page shows an honest error state, not stale numbers. The JSON files + importers are then deleted.
Auth + validation reuseWrites reuse the existing require_admin dependency (X-Admin-Secret, fail-closed) — the same gate the private read endpoints use, no new auth. Request bodies are validated by Pydantic schemas (wrong shape → 422, never a dirty row).

Phone MCP connector — daily-log CRUD from Cowork

✅ Done · live · phone-verified v0.9.0

Let a phone / Cowork chat create, read, edit and delete the daily log by talking to the backend as MCP tools through a claude.ai custom connector — no laptop, no ~/.til-env, no git.

Why a connector, not bashThe Cowork cloud sandbox blocks bash egress to lia-til.onrender.com (curl → 403/000), but an MCP connector rides a different transport that does reach it. So a connector is the path to touch the log from the phone. Caveat: interactively-authed connectors may be absent in headless/cron runs — this reliably powers interactive phone-chat logging, not (yet) the unattended scheduled check-in.
A

Backend — mount an MCP server on the same FastAPI app

Library
fastmcp>=3.4 (needs Python ≥3.10, so a .python-version = 3.12.7 pin was added). One deploy, zero new infra — the MCP app is mounted onto the existing FastAPI app, reusing the same Neon DB and handlers.
Tools
main.py exposes 8 tools: list_daily_logs, get_daily_log, upsert_daily_log, patch_daily_log, append_section (get→merge→save one heading without clobbering the rest), delete_daily_log, get_index, set_index. They call the same handlers as the HTTP API, so every write still flows through _shadow() append-only backup.
Scope
Mirrors require_daily_writer: daily-log + index ONLY — never applications, résumés, LeetCode, or destructive table ops. A leaked connector can only touch the daily log, and even that is recoverable via the master-only shadow restore.
Transport
Stateless Streamable-HTTP (mcp.http_app(path="/", stateless_http=True, host_origin_protection=False)); its session manager is started from the app's lifespan. Origin protection is off because the URL token (below) is the auth and Render's proxy would otherwise trip DNS-rebinding checks.
B

Auth (Option 1 / MVP) — a secret URL token

The whole MCP app is mounted under an unguessable path, /mcp/<MCP_TOKEN>/ — knowing that URL is the credential; a wrong/absent token just 404s. MCP_TOKEN is a secrets.token_urlsafe(32) string kept in Render's env (never committed).

Deploy
Set MCP_TOKEN on Render (alongside the existing BACKEND_SECRET + DAILYLOG_SECRET) → push to main → Render auto-deploys. Verified locally: the 8 tools list, a full CRUD round-trip works, patch preserves untouched sections, and a wrong token → 404.
Connect
On the phone / claude.ai → Settings → Connectors → Add custom connector → paste https://lia-til.onrender.com/mcp/<MCP_TOKEN>/; leave the OAuth Client ID/Secret blank (authless). claude.ai strips the trailing slash and GETs the no-slash path, which 307-redirects to the slash form and connects fine (GET on the endpoint → 405, spec-OK).
Gotcha
Saving/changing MCP_TOKEN on Render triggers a restart, so the endpoint 404s for ~30s — a 404 right after an env change usually just means "still restarting", not a code bug.
