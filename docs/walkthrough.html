P1 · S1

First Deploy

✅ Done v0.1.0

Deploy the Next.js walking skeleton to Vercel and get a public URL anyone can open. The whole point of this stage is proving the "edit file → push → auto-deploy" pipeline end to end — once it works, every later stage deploys for free.

A

Start in parallel

Both steps run at the same time — they don't depend on each other.

  1. 1
    Me · terminal

    Verify build locally + merge to main

    Run a production build to confirm web/ compiles, then merge the skeleton branch into main and push. Vercel's production deploy tracks main.

    cd web && npm install && npm run build
git checkout main && git merge feat/phase1-web-skeleton
git push origin main
  2. 2
    You · browser

    Sign in to Vercel with GitHub

    Open vercel.com → Continue with GitHub, pick the free Hobby plan. When authorizing, granting the lia-til repo is enough.

    NoteSigning in / authorizing is something only you can click — I never touch your account.
B

Import & configure

All in the Vercel UI — this is where the one real gotcha lives.

  1. 3
    You · browser

    Import the lia-til repo

    Add New… → Project → find patelinadev/lia-til → Import. Don't see it? Click Adjust GitHub App Permissions and add it.

  2. 4
    You · browsercritical step

    Set Root Directory to web

    On the Configure screen → Root Directory → Edit → select web. The Next.js app lives in a subdirectory; skip this and the build fails / renders blank — the one gotcha of this whole setup. Once set, the Framework Preset auto-detects Next.js.

  3. 5
    You · browser

    Click Deploy, wait 1–2 min

    No environment variables, no database — just hit Deploy. All green means success.

C

Get the URL & verify

  1. 6
    Verify

    Check against the acceptance criteria

    Stage 1 acceptance

    • Open the URL in an incognito window (or send it to someone) — visible with no login.
    • The page renders the progress content correctly.
    • Ask me to change one thing → push → the change is live after ~1 min (pipeline proof).

    ✅ All three passed — verified auto-deploy by pushing the "landing copy → English" change. Stage 1 shipped.

Troubleshooting

Q1Vercel build fails / blank page / 404
Almost always Root Directory isn't set to web. Settings → General → Root Directory → set web, then Redeploy.
Q2Can't find lia-til when importing
Click Adjust GitHub App Permissions and grant Vercel access to the lia-til repo.
Q3Pushed, but the site didn't change
Confirm you pushed to the production branch main. Vercel's Deployments tab shows every build triggered by a push.
P1 · S2

Section Routes + Daily Log Timeline

✅ Done v0.2.0

Turn the placeholder skeleton into a real site: a minimal home hub that links into two separate section routes — a LeetCode table and a Daily Log timeline — so nothing piles onto one long page. Data comes from JSON files in the repo — still no backend, no database, no new dependencies.

KeyS2 needs no new deployment setup. S1 already wired the Vercel pipeline — from now on, deploying any content stage just means the standard git flow: push to main, it auto-deploys. That's the payoff of building the walking skeleton first.
A

Structure — a hub + section routes

Home stays minimal; each section gets its own page. Grew to four sections over S2.

  1. 1
    App Router

    A hub that links into four sections

    /              # minimal hub → four entry cards ("Today I Learned")
/leetcode      # problem table — header-dropdown filters, sort, colored topics
/daily-log     # tree-trunk day-by-day timeline
/applications  # anonymized dashboard + Monday-start submissions calendar
/system-design # source→chapter tree; /system-design/<slug> per-deck detail

    Built with next/link; every route prerenders as static. A subtle global footer credits "Developed by Lia".

  2. 2
    /leetcode

    All 15 solved problems, filterable & sortable

    #ProblemTopicDifficultyStatusDate
    42Trapping Rain WaterTwo PointersHardFirst pass08/05
    713Subarray Product Less Than KSliding WindowMediumFirst pass08/10
    • Columns: Problem + Solution links · Topic (multi-select, each a distinct color via golden-angle hue) · Difficulty · Status (5 states in 3 groups) · Date (last completion). All scraped from 0x3f-study-plan.md; dates recovered from the daily-log sweep.
    • Sort — click the #, Difficulty, or Date headers (asc → desc → default episode order).
    • Filter — dropdowns that open from the Topic / Difficulty / Status column headers (Difficulty both sorts and filters). The Status filter shows the 5 status tags grouped under 3 category headers (To Do / In Progress / Complete) — you pick one of the 5 — with the grouping logic explained inline.
    Why it fits S2Filter/sort is client-side view state (a Client Component with useState) — no persistence, no backend. That's why it stays in Phase 1. lib/content.ts was split into a client-safe half + a content.server.ts (fs readers) so the browser bundle doesn't pull in node:fs.
  3. 3
    /daily-log

    Tree-trunk timeline (newest first, scroll for history)

    A vertical trunk on the left; each day branches out to the right — header W## · mm/dd/yyyy, then that day's ✅ checked items and a one-line summary (you write it; I can draft first). Note days show a single "📝 Wrote notes: …" line — never the full notes.

    • Scroll-reveal micro-animation — nodes fade + slide in on scroll, via a tiny IntersectionObserver client component (app/components/Reveal.tsx). Zero dependencies; respects prefers-reduced-motion.
    • LeetCode kept in the log — a day's LeetCode problems render as ✓ chips matching the done items. Each links only to Lia's own solution write-up (un-linked if no solution yet). Solution URLs are single-source in leetcode.json, looked up by id — so adding one there auto-fills the log.
    • 20 curated days scraped from the Obsidian daily logs, privacy-filtered.
    LanguageEnglish-only, no exceptions — every field of the daily log (to-dos, summaries, and the 📝 note) is English, same as the rest of the site.
  4. 4
    /applications/system-design

    Two more sections added over S2

    • Applications — an anonymized job-search dashboard (total + a Heard-back / Interviewing / Closed funnel) and a Monday-start calendar showing each day's submission count. Built from a local, git-ignored ledger via a generator that emits only aggregate counts — no company names ever reach the repo (see Privacy).
    • System Design — a source→chapter tree (30 decks by phase); each completed deck is its own route /system-design/<slug> with a sticky Google-Docs-style outline. Diagrams are re-drawn as theme-aware HTML, not screenshots.

🔒

Privacy (applies to every update)

Obsidian source files never enter the repo. The repo is public, and the logs contain sensitive material (PhD applications, Success Diary, contact info). We curate rather than sync: only the publishable subset ships (solution links + study-type checked items + a one-line summary you approve). Sensitive items are excluded by default, each passed through a §6 warning check for you to confirm.

Example (8/16): the original had "application material audit (SOP / CV / recommendation letters / deadline)" — revealing grad-school applications — so it was genericized to "Reviewed application materials"; the application count was kept.

Daily update loop (every day after S2)

You drop solution links / today's checked items → I append JSON + you approve the one-liner → git push → Vercel auto-deploys
Phase 2

Cloud Backend

🗺️ Planned v0.3.x (target)

One cloud backend — FastAPI on Render + PostgreSQL on Neon (both free) — as the single source of truth (applications / LeetCode / daily log). You edit in one place; the site fetches the latest on every open; you log in to see full private data. Full design: docs/requirements-v2.0.md.

DecidedSite reads the backend at request time (dynamic — open = latest, no rebuild). Admin = private routes inside the same app, GitHub-login-gated. Public still gets aggregates only (§6 holds).
S1

Backend skeleton + Applications

Prove client → server → DB → deploy with the cleanest data line first.

  1. 1
    You · Neon + Render

    Create a Neon database + a Render service (both free)

    Create a Postgres DB on Neon (free serverless Postgres); create a free web service on Render connected to the repo's backend/; set DATABASE_URL + env vars. Accounts + secrets are yours — I don't touch credentials. (Not Railway — its free tier is gone and paying adds no résumé value; the host name isn't the skill.)

  2. 2
    Me · backend

    FastAPI + applications schema + importer

    Scaffold FastAPI, an applications table (+ status events), a one-time importer for the local ledger, and a public aggregate endpoint (counts only — no company data).

  3. 3
    Me · site

    Site fetches the aggregates at request time

    Point /applications at the API (dynamic), replacing the build-time JSON.

  4. 4
    Verify

    Numbers come from the DB

    Open /applications → the counts are served from Postgres, not a committed file. No rebuild needed.
